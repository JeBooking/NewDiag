# 文件与现场参数修复交付

## 根因与处理

- 启动参数原来只有四种控件，上传引用没有在初始化调用前转换成服务器路径；新增 file 控件与统一文件引用校验，业务收到普通路径字符串。
- 实例方法沿用旧函数的严格发布规则，无来源必填参数被要求提前放到开始节点；新增节点 runtimeInputs 和 parameters 待办，到达节点才填参并执行。显式现场输入不再冻结旧的同名方法局部启动字段。
- 后端 JSON 调用本来能传列表、字典，页面控件与发布类型限制阻断实际使用；统一扩展为八种表单类型，array/object/json 保持结构，不重复编码成字符串。
- 默认值逻辑原来把 null 视为未填；JSON 的显式 null、空字符串，以及空数组、空对象均保留为值。

执行到现场待办时尚未调用业务方法；提交校验失败或方法失败保留待办，可修正后重试。恢复使用当前执行代最新对象及资源视图，保留等待期间同级分支写入的成员与缓存。

没有新增依赖、API 路径或数据库列。未配置现场输入的旧启动来源、历史发布版本和四阶段流程继续兼容。
普通 self 成员仍按整对象保存恢复，恢复边界继续留在 TODO。

## 验证

修复回归：完整后端 `pytest backend/tests -q` 为 **154 passed**。覆盖启动文件引用、伪造路径／失效引用拒绝、数组及对象结构、JSON null、缺来源自动现场填参、旧启动字段移除、业务错误重试、重复提交、人工判断后成员恢复、等待期间同级分支缓存与成员保留。
前端 `pnpm type-check`、`pnpm build` 均通过。

在隔离本地数据目录实际打开生产构建，手工结果：

1. 节点方法面板可为每个参数选择现场填写，类型下拉显示八种类型，数组、对象、上传文件配置正确。
2. 启动页上传 report.json，数组输入改成非法 JSON 后点击开始，被阻止且显示错误；改为 `["A","B","C"]` 后成功启动。
3. inspect 到达时出现参数待办，数组／对象默认值为原结构，现场上传 evidence.json 成功。
4. 提交 samples=`[]`，业务提示至少提供一个采样值，待办与已填文件保留；改为 `[1,2,6,3]` 后执行成功，展示证据、曲线、通道数量 3 和峰值 6。
5. 填写判断依据并选是后流程完成；后续节点运行依据显示「等待后保留 4 个采样值，峰值 6」，没有剩余待办。

首次全量检查中，新测试在收集阶段过早导入 API，导致既有 SSE 用例绑定到初始化前数据库；已将新测试改为直接引用调度服务，消除收集顺序影响，完整重跑通过。
