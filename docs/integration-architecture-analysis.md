# 基于现有实现的三工程接入架构分析

2026-11-06；架构建议，待确认后进入 spec。本文替代先前 project-composition-proposal.md 的架构建议，不修改现行契约。

本分析的“当前实现”指改造前 v1.12。获授权后的实现契约已同步到 spec.md v1.13，使用步骤见 composition-integration.md。

分析基线：当前 diagnosis/v1 诊断实例方案。已废弃的四阶段方案不参与架构选择、复用评估或本轮兼容范围。

## 1. 结论与约束

推荐：平台管理一个逻辑诊断实例，实例包含多个工程的普通业务对象；以配置声明启动资源、按需资源和节点操作；每个工程使用自己的业务进程，跨工程通过明确的数据或文件边界衔接。

保留现有 doc → plan → Scheduler、人工待办、执行轨迹、按到访回退、实例隔离和对象快照机制。将原来由业务诊断类承担的调用组合移入平台，不再要求接入方写一个新的总控诊断类。

已明确的要求：

- 五组人员分别维护取数、解析展示、判断、平台和流程。模块维护者只面对代码，通过公开接口、签名及注释表达模块能力，不登录平台登记或授权接口。
- 编排团队登记工程并选择公开接口、配置参数和连接关系；可以理解技术接口，无需手写串联代码。
- 原项目允许少量接口抽取、桌面输出分离；保留业务算法，不另建集成项目复制逻辑。
- 启动时完成主要数据的获取和解析，正常运行期间保存在业务进程内存；额外数据首次需要时获取解析，实例内按有效参数缓存。
- 绘图和判断使用同一份解析／处理数据。图表首期为静态图片、点击在独立窗口查看。
- 沿用当前对象全量保存恢复边界；运行资源的排除和重建仍按 docs/todo.md 暂缓，不在此次架构中偷偷引入另一套规则。

## 2. 当前代码已经解决什么

| 能力 | 实现与实际边界 |
|---|---|
| 发布编译与参数绑定 | services/compiler.py 的 compile_doc、_resolve_args；显式绑定、启动输入、上游结果、默认值和歧义检查已具备 |
| 初始化与逻辑实例 | worker/diagnosis_sdk.py 的 DiagnosisRuntime；initialize 只在首次启动执行 |
| 普通成员与对象图恢复 | artifacts.save_python/load_python；DiagnosisRuntime 对整个业务对象做 pickle，不要求 self.data |
| 首次访问缓存 | ResourceCache；归一化默认值、参数键、内存命中、持久化引用、失败不缓存、并发同请求合并 |
| 人工等待与回退 | Scheduler 保存状态引用，关闭业务会话，继续时恢复；generation 和具体到访确定继承视图 |
| 大数据与图片存储 | artifacts 的 JSON 字段索引、Python 对象快照；node_sdk.save_file 和 files 内容寻址 |

当前真正的耦合：

1. 新建流程使用 instance_doc，进入 diagnosis/v1；整图绑定一个 Diagnosis 子类，获取、解析、绘图与判断的组合由该类的方法实现，因此接入方仍需编写总控业务类。
2. SessionManager._handles 按 instance_id 保存单个 handle；切换 path/module/python/factory 就关闭旧进程，各工程对象不能同时存活。
3. DiagnosisRuntime 通过一个业务类的 config 创建对象，尚不能根据配置创建、命名和组合多个原工程普通对象，也不能把对象返回值登记为后续调用目标。
4. 诊断节点的方法必须返回 presentation/result/reason；原工程的方法无法直接把原始结果分别配置成展示、判断和依据。
5. 排查节点只绑定该诊断类的一个方法，JudgeEngine.judge_series → summary 这样的组合仍需写在业务方法内。
6. 模块、方法、构造器发现与返回描述不足。前端有 doc 字段，但后端未提取和传递 docstring。

## 3. 架构选项与选择依据

| 方案 | 优点 | 主要成本 | 建议 |
|---|---|---|---|
| 继续要求业务方手写总控 Diagnosis 类 | 现有运行机制几乎不变 | 每条业务组合仍需要胶水代码和新的维护归属 | 保留给需要写代码的高级接入，不作为本次主路径 |
| 一个业务进程导入所有工程 | Python 对象直接共享，最接近手写普通程序 | 强制统一依赖、解释器、模块搜索路径及全局状态；三个独立维护团队相互牵制 | 不作为默认架构；以后可在明确兼容时优化 |
| 一个逻辑实例＋多个工程进程＋配置组合 | 保留模块独立环境和内存对象，统一初始化、缓存、回退 | 需扩展会话管理、对象引用与组合计划 | 推荐 |

多进程的理由是隔离依赖与运行状态，不是把各模块改造成网络服务。首期仍为同一后端机器上的本地 worker，无需每个团队维护 HTTP 服务，也不引入消息队列或分布式调度。

## 4. 推荐的四层结构

### 流程层

保留业务画布。开始、排查、结论、处置、人工动作、终止仍由 Scheduler 解释执行。

开始节点执行平台配置的启动资源准备；排查节点绑定一个可复用操作，补充指标、阈值、设备等业务参数。取数、加载对象、绘图、汇总结论不强制各占一个主画布节点。

### 组合配置层

流程配置增加三个概念，具体字段名在正式修改 spec 时确定：

- 工程对象：选择构造器或工厂，配置构造参数；对象由一次诊断持有。工厂返回的新对象也可命名保存。
- 数据资源：一组获取、解析调用及其命名结果。触发策略为启动准备或按需；按需资源可依赖其他资源，依赖必须无环。
- 节点操作：为完成一次业务排查而执行的有限、有顺序调用，引用资源和参数，声明展示和判断输出。

接口选择支持模块函数、类方法、实例方法、对象返回值的方法。参数可来自启动输入、常量、资源、前面调用、上游结果和平台输出路径；支持字段选择及列表／字典组合。平台不加入任意 Python 表达式编辑、循环或用户脚本。

复杂滤波、特征提取、图形构造等业务逻辑留在原模块接口内。若必须在配置里重新实现算法，说明业务接口还未抽取到合适粒度。

操作与资源模板可以复用，发布时将展开配置冻结到流程版本。模块维护者不维护平台模板；模板由编排团队创建并使用。

### 实例运行层

平台建立组合实例运行时，统一管理各工程对象、资源缓存和状态清单。现有 DiagnosisRuntime 的生命周期语义保留，但普通业务对象无需继承 Diagnosis，也无需返回平台专用字典。

每个实例按工程登记身份维护 worker；每个 worker 支持多个模块，使用本工程解释器和工作目录。构造器和工厂均可配置为对象创建入口。

worker 内维护一组真实 Python 对象及对象句柄。同工程的 Dataset、Record、Verdict 列表直接以对象传递，句柄只在其所属实例／worker／状态版本内有效，不能当作跨工程数据。

跨工程值只有三种处理：小型结构化值直接传；大型 JSON 数据保存为不可变产物引用，由消费者 worker 加载并按需要保留内存；文件先收集为不可变产物，再提供读取路径。诊断运行状态继续由平台现有的 diagnosis_states、状态清单和 artifacts 机制保存恢复，其中 Python 对象产物在所属业务进程恢复；不是保存恢复工程源码或运行环境，也不是增加一套独立的 pickle 恢复机制。

### 记录与存储层

现有 runs、reviews、tokens、diagnosis_states 和 artifacts 继续承担记录职责。状态引用从单个诊断对象扩展为组合实例清单，列出各工程对象图快照和各资源结果引用。

SQLite 保存状态与引用，不存业务大对象。内存对象供正常调用；持久快照供人工等待、进程重建和回退，两者用途不同。显示层只拿展示描述和附件引用，不接收 Dataset 等业务对象。

## 5. 三个工程的实际接入

### 数据获取模块

直接使用 DataClient(root, interval) 和 fetch(...)，root 绑定平台分配的输出目录。每次实际调用分配独立目录，避免相同参数的默认文件名覆盖旧文件。

fetch 返回 pathlib.Path。平台通过明确的文件输出配置收集、固化文件，并将可读取路径传给 PlotEngine；不能把 Path 转成 repr 后再调用 Dataset.load。

DataClient.query 也是可选现有接口，但 Dataset 当前读取文件。首期使用 fetch → load 能复用现有完整路径，额外磁盘开销可后续优化；文件是取数和解析边界，不是每次绘图都重新读取。

### 解析展示模块

Dataset.load(path) 在启动资源中调用，Dataset 对象保存在 PlotEngine worker。后续 Dataset.plot_series(device, activity, metric, ...) 从该对象提取同一版曲线，所得数值字典同时用于绘图和判断。

plot_window.save_plot 已有纯图片输出接口，可直接作为绘图调用；平台提供输出路径并收集图片。当前模块顶层仍导入 tkinter/TkAgg，部署无 Tk 时应把桌面导入移到桌面实现内，保留纯渲染入口。

Flow.py 是现有的业务组合示例，FlowClass 同时依赖 SDK、Dataset 和 JudgeEngine。平台分别组合三个工程后，不应要求继续往 FlowClass 追加总控逻辑。

对 draw_1/draw_2 必须保留的既有绘图处理，应给原绘图方法增加无窗口导出入口或可替换的输出后端，复用同一计算逻辑。多曲线循环等仍在 PlotEngine 内完成，不要求编排团队重建循环。示例中的基础单曲线可直接用 plot_series＋save_plot；真实复杂绘图优先调用原业务方法。

应把供平台调用的解析／绘图入口放在不依赖判断模块的公开模块中。可在原项目内抽取既有逻辑，桌面 FlowClass 继续调用这些入口；这属于模块接口整理，不是另建总控项目。

### 判断模块

JudgeEngine(thresholds=...) 创建在 JudgeEngine worker。该 worker 接收同一版曲线，执行 judge_series(item)，然后在同进程把 Verdict 列表传给 summary(verdicts)。原始对象不会经过 JSON/repr 损坏。

平台配置将 summary.overall 映射为 yes/no，summary.reasons 展示为依据，summary.verdicts 展示为明细表。无触发时使用明确的正常依据模板；异常／缺字段报执行错误，不能当作 no。

JudgeEngine 默认包含 peak、mean、trend，单填 peak 阈值不会关闭其他规则。只做峰值判断应选已有 PeakThresholdRule.evaluate 或 judge(..., rule='peak')，再按实际返回形态配置映射。

### 一次运行

```text
启动表单
  → 获取主数据文件
  → Dataset.load：解析一次并保留 Dataset
  → 完成启动检查点

进入振动排查
  → Dataset.plot_series：从现有 Dataset 选择曲线
  → 同一曲线 → 既有绘图方法／save_plot → 图片
             → JudgeEngine → summary → 判断和依据
  → 平台组合展示并推进是／否分支，或等待人工判断

进入后续排查
  → 继续使用 Dataset
  → 需要额外数据时调用按需资源；首次获取解析后缓存
```

## 6. 缓存、状态和回退

启动资源是实例初始化的一部分，不以绕回开始节点刷新。按需资源在首次执行到需要它的操作时加载，失败未完成的资源不标记成功缓存。

缓存键包括资源定义身份／版本和归一化业务参数，依赖资源也要关联具体版本。不同请求各有结果。不是按画布节点 ID 缓存，因此多个节点可共享同一资源。

资源结果和文件固定版本；普通对象图沿用当前整体保存。每次节点完成或进入人工等待前建立组合检查点，只有相关 worker 快照全部完成后才发布新的清单引用。执行错误保留诊断证据，但不能把未完成资源伪装成可用数据。

人工等待时可沿用现有释放进程策略；再次执行业务调用时恢复对象，不重跑 initialize、不重新取数。正常运行期间不在每次方法调用前反序列化 Dataset；当前 worker 已持有目标版本时继续使用。

回退仍以具体到访和 generation 选定历史视图，恢复该版本的各工程状态及缓存。现有语义中，回退到尚未加载某按需资源的旧视图，后续首次需要时可能再次获取；不能为了“曾经获取过”而偷用较新视图数据。

当前 Scheduler 的 parallel 是分支推进语义，_step 仍逐个调用节点并持有实例操作锁。首期保留此执行方式，资源副本／只读策略沿用现有保护，不为本次接入额外引入节点真正并发。

终止实例时取消调度并关闭它的所有 worker；重建某 worker 后只恢复其有效状态，已经失效的句柄必须拒绝。原来只清一个 handle 的路径需要全部检查。

对象含锁、窗口、活连接而不能 pickle 时，沿用当前明确报错规则；不宣称该架构已解决全部运行资源恢复。平台进程重启自动续跑仍不包含在此次接入目标内。

## 7. 公开接口、类型和版本

模块方通过公开模块、__all__、公开方法和签名管理接入面；平台正确支持普通类构造、class/static method 和返回对象。需要明确可发现不等于自动执行，扫描不能自动实例化所有类或调用业务方法。

docstring 是给编排团队看的说明，自动读取即可；不从注释推断业务行为，不要求维护者额外操作平台。缺少类型注解时，平台允许编排者在绑定时声明所需类型并校验样例，不能假定所有值都是文本。

允许接口带 **kwargs 而只绑定其显式参数，例如 save_plot 和 judge_series。扩展参数另行配置为明确字典并检查冲突；首期不必支持所有可变位置调用形式。

发布冻结对象定义、资源依赖和触发策略、节点操作、参数与类型映射、结果映射、展示以及接口指纹。复用模板修改不会改变旧发布版本。

现有接口指纹不能发现同签名算法变化。三团队独立维护时，应记录源码版本／包版本或代码摘要，启动发现版本变化时要求重新确认发布；记录版本不等于归档运行环境，不承诺任意历史版本可在新环境重放。

## 8. 实施边界

| 位置 | 必要改造 |
|---|---|
| domain/types.ts、schemas、spec | 扩展当前诊断实例配置，描述多个业务对象、资源、节点操作及产物；精确字段在确认后统一定义 |
| probe/projects/signatures | 多模块、普通构造器／方法／对象接口、docstring、统一元数据与版本信息 |
| compiler | 将配置编译成资源和操作计划；检查依赖、来源、对象所属工程及结果映射 |
| sessions | instance → 多工程 handle；取消、超时、关闭、恢复范围同步扩展 |
| worker/session | 对象注册与调用、同进程对象引用、文件和 JSON 产物；不再强制普通返回对象转换成 repr |
| diagnosis_sdk/artifacts | 提取可复用缓存与快照组件；保留旧 DiagnosisRuntime，增加组合实例状态清单 |
| scheduler | 开始执行启动资源、节点执行操作、按需加载与检查点；保留原有路由、人工和回退框架 |
| 配置界面 | 启动／按需资源配置、节点操作编辑、参数及结果选择、可复用模板；不是让每个编排者重复拼完整调用链 |
| 图片展示 | 沿用 image/附件机制，补齐点击独立窗口查看 |

改造沿当前诊断实例方案推进：把必须由一个业务类手写的初始化、资源加载及节点组合扩展为平台配置；继续使用同一套逻辑实例、检查点和调度语义。废弃方案不作为新模式的实现基础，也不为其安排额外兼容工作。

建议先实现能够在多工程间稳定保存普通对象和传递文件／数据的运行基础，再接启动资源和一个排查操作的完整配置链，最后做模板复用及编辑体验。新增开发按用户要求不自动运行测试；本文为静态分析，尚未实施、未运行外部项目。

## 9. 何时仍需要模块改动

- 逻辑只能通过按钮或窗口事件触发：抽出原处理函数，提供程序调用入口。
- 只显示不输出：补静态图片或结构化结果出口。
- 跨模块必须共享同一个不可导出的业务对象：在所属模块提供数据投影接口；不自动跨解释器传对象。
- 核心状态无法保存恢复：触及当前明确暂缓的运行资源边界，需要单独解决，不能靠配置掩盖。
- 某接口必须人工参与或具有不可重试副作用：用人工节点或明确的调用策略表达，不能自动当作普通只读取数。
- 私有服务、设备、依赖或授权对执行环境不可达：先提供可运行的部署环境。

此架构的目标是由平台完成可机械化的接口调用组合；业务算法、数据含义和必要的程序调用入口仍由原模块维护。
