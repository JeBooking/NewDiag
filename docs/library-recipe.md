# 能力配方开发手册

把已经能跑的库直接接进诊断流程，不需要为它们写适配类、也不需要把取数/绘图/判断拼成新项目。

---

## 1. 为什么需要它

旧接入方式要求业务侧交出一个"平台形状"的东西：

| 方式 | 业务侧要做什么 | 代价 |
|---|---|---|
| 诊断实例类（diagnosis/v1） | 写一个 `Diagnosis` 子类，把取数、解析、绘图、判断都塞进同一个类 | 三个现成库要粘成一个新类，库自己的 API 被包一层 |
| 四阶段函数（investigation/v1） | 写适配器类，实现 acquire/parse/present/judge | 同上，还得按平台协议拆阶段 |
| 直接绑定函数（call） | 只支持 JSON 返回值，对象活不过一次调用 | 拿不到 Dataset / 绘图对象，只能一路落盘再读 |

三个库各自都是完整的：`DataClient.fetch` 取数、`Dataset` + `save_plot` 绘图、`JudgeEngine` 判断。
真正缺的不是能力，是**把它们串起来的那层胶水**，以及**画出来的图怎么到人眼前**。

能力配方（`library/v1`）补的就是这两件事：

- 一个节点内可以按顺序调用任意多个现成函数，中间对象留在进程里，不用序列化；
- 节点之间只传 JSON（文件路径、结论、阈值），由平台已有的上游输出绑定负责；
- 返回值自动变成运行记录里的图、曲线、表格、指标，不用写展示代码。

结果：接入三个库只写了一份 JSON 流程，业务代码零改动。

---

## 2. 三个概念

### 节点 = 一次能力装配

一个节点声明一个工程，以及按顺序执行的若干步骤。步骤之间用 `as` / `$var` 传对象：

```json
{
  "kind": "capability",
  "title": "装配并绘图",
  "recipe": {
    "protocol": "library/v1",
    "project": "绘图引擎",
    "steps": [
      {"call": "Dataset.load", "args": {"path": {"$run": "n1", "path": "output.data_file"}}, "as": "dataset"},
      {"on": "dataset", "call": "plot_series", "args": {"metric": {"$snapshot": "metric"}}, "as": "series"},
      {"call": "plot_window.save_plot",
       "args": {"data": {"$var": "series"}, "path": {"$file": "curve.png"},
                "title": {"$var": "series", "path": "label"}},
       "as": "image", "show": "image"}
    ],
    "out": {"image": {"from": "image"}}
  }
}
```

- `Dataset` 对象只活在这一次节点执行里，不会被序列化，也不需要另一个库认识它；
- `curve.png` 由平台分配可写路径，写完自动登记成附件、变成 `image` 展示块。

### 对象不出进程，跨节点只传 JSON

| 作用域 | 能传什么 | 谁负责 |
|---|---|---|
| 节点内部（步骤之间） | 任意 Python 对象 | 业务进程，`as` + `$var` / `on` |
| 节点之间 | 只有 JSON | 平台，`out` + `{"$run": 节点, "path": "output.字段"}` |

这不是限制，而是分工：同一节点里的步骤天然属于同一个库，对象直接传最省事；
跨节点必须是可审计的数据，才谈得上"运行记录里能查"。

### 展示物化，不写展示代码

每个步骤的返回值按 `show` 变成展示块：

| `show` | 行为 |
|---|---|
| `auto`（默认） | 图片/曲线/表格/指标才出块；路径、普通字符串、对象都不出块 |
| `text` | 强制按文本展示（取数落盘路径适合这一档） |
| `table` | 列表或 `as_dict()` 对象 → 表格 |
| `line` | 数字序列或 `{x, y}` → 曲线 |
| `image` | 图片路径 / `bytes` / matplotlib `Figure` → 附件图 |
| `none` | 不展示 |

物化在业务进程里完成，平台只收展示块（和四阶段协议的 `presentation` 是同一套结构），
所以运行记录、人工待办、回放页面用的是同一个渲染器。

## 3. 接入一个新库：四步

### 第 1 步：登记工程

「工程」页填四项，和旧接入完全一致：

| 字段 | 说明 |
|---|---|
| 名称 | 流程里引用它的键，登记后不可改 |
| 路径 | 工程根目录，会话进程的 `cwd` |
| 模块 | 入口模块，如 `dataclient`、`dataset`、`judgekit` |
| 解释器 | 留空用平台解释器；有第三方依赖的库填它自己的 venv |
| 工厂 | 留空表示模块本身作为根对象；填 `DataClient` 表示先构造实例 |

解释器这一项最容易踩坑：绘图库依赖 matplotlib，平台自己的环境通常没有，
要么填该库的 venv，要么在平台环境里装同一套依赖。

### 第 2 步：在画布上放一个「能力步骤」节点

节点类型选**能力步骤**。它只有一个默认出口，本身不做是/否判断——判断交给排查节点。

> 为什么单独一种节点：取数和绘图不产生"是/否"，硬塞进排查节点会让流程出现两个假分支。

### 第 3 步：写步骤

属性面板里选工程，逐个添加步骤。每步填四样：

| 字段 | 说明 |
|---|---|
| 调用 | 点分名，如 `Dataset.load`、`plot_window.save_plot` |
| 对象 | 留空从工程根解析；填变量名表示在该对象上调用方法 |
| 保存为 | 把返回值存成节点内变量，供后续步骤 `$var` 引用 |
| 展示 | 见上表 |

`调用` 的解析顺序（`backend/app/worker/library_sdk.py: resolve`）：

1. 从根对象（模块或工厂实例）按点号逐级取属性；
2. 取不到就把前缀当模块 import：`plot_window.save_plot` → import `plot_window`，取 `save_plot`；
3. 都没有才报错。

所以一个工程里跨子模块的能力可以直接点名，不需要改 `__init__.py` 的导出。
解析到**类就构造，解析到函数就调用**：`JudgeEngine` 是构造，`Dataset.load` 是调用。

### 第 4 步：声明对下游的输出与判定

- `out`：暴露给下游的 JSON 字段，下游用 `{"$run": "节点id", "path": "output.字段"}` 引用；
- `result`：只有排查节点需要，指向 `yes`/`no` 字段；留空表示"算完停下来让人判断"；
- `reason`：自动判定必须写依据，支持 `{保存名.字段}` 插值；
- `evidence`：把某个上游节点的图一起带进本次待办，执行人不用去轨迹里翻。

## 4. 参数表达式

`args` 里以 `$` 开头的对象是表达式，其余结构原样递归求值（所以字面量里也能嵌表达式）。

| 写法 | 含义 | 求值方 |
|---|---|---|
| `{"$snapshot": "name", "cast": "number"}` | 开始节点声明的启动参数 | 平台 |
| `{"$run": "n1", "path": "output.data_file"}` | 上游节点的输出字段 | 平台 |
| `{"$var": "series", "path": "y"}` | 本节点前面步骤保存的对象 | 业务进程 |
| `{"$prev": true, "path": "..."}` | 上一步的返回值 | 业务进程 |
| `{"$file": "curve.png"}` | 分配一个可写路径，返回绝对路径字符串 | 业务进程 |

`cast` 只在需要时写：启动表单的值默认是字符串，要参与数值比较就写 `number`，
要传结构化数据就写 `json`，要布尔就写 `boolean`。

`$file` 是整个方案里唯一"平台偏心"的地方：它替业务库挑了一个可写位置，
目的只有一个——**返回值是文件时，平台知道该把它收成附件**。

## 5. 执行语义

- 步骤按声明顺序在**同一个进程**里执行，任何一步抛异常整节点失败，错误带调用名；
- 调用前会按真实签名 `bind` 一次，参数写错直接报"参数不匹配"，不用等 TypeError；
- 节点超时、进程崩溃沿用平台的会话重试（一次）；业务异常不重试；
- 一个节点只属于一个工程，切换工程意味着换会话进程，所以**对象不跨工程**；
- 人工等待不关会话（对象已经用完），终止、回退、分支、并行/串行全部沿用原调度器。

回退到配方节点时按"重执行"或"复用分支"两种模式走，和函数绑定节点一致；
历史 run 不会被覆盖。

## 6. 展示与审计

运行记录里每个配方节点会留下三层信息：

| 位置 | 内容 |
|---|---|
| `run.input` | 每个步骤求值后的实参（不含对象，对象只记录类型） |
| `run.output` | `out` 字段 + `result` + `reason` |
| `run.evidence` | 展示块、分支、每步耗时与返回类型、`evidence` 合并结果 |

图片走内容寻址附件：同一张图重复生成只存一份，待办与历史记录引用同一个摘要。

## 7. 与其它协议的关系

| 协议 | 什么时候用 |
|---|---|
| `library/v1`（本文） | 库已经有清晰 API，只想拼装和出图；不写业务代码 |
| `diagnosis/v1` | 一个业务类天然承载整次诊断，且需要在人工等待后恢复对象状态 |
| `investigation/v1` | 已有四阶段适配器，或必须按采集/解析/展示/判断拆开 |
| 旧 `binding` | 单个函数、入参出参都是 JSON 的简单场景 |

同一个节点只能选一种；同一张图里可以混用（比如取数用配方、判断用诊断类方法）。
诊断类流程（`doc.diagnosis`）不允许再放能力配方节点。

## 8. 已知边界

| 边界 | 现状 | 影响 |
|---|---|---|
| 对象不能跨节点 | 只传 JSON | 需要"上一节点的 Dataset"时，把相关步骤放进同一个节点 |
| 跨工程不能传对象 | 切工程即换进程 | 跨工程靠文件路径/JSON，和本例一致 |
| 对象方法的参数不在发布期校验 | `on` 步骤没有静态签名 | 运行期 `bind` 报错，错误信息带调用名与参数名 |
| 只支持同步函数 | 与平台其它协议一致 | 异步库需要库方提供同步入口 |
| 不代渲染桌面窗口 | 需要库自己有无头导出函数 | PlotEngine 用 `save_plot`，不是 `show_plot` |
| 启动参数只读全局作用域 | `{"$snapshot"}` 取 global | 函数级启动参数请用诊断类模式 |
| 无自动重试语义 | 沿用平台一次重试 | 有副作用的库请自行保证幂等 |

## 9. 排错

| 现象 | 原因 | 处理 |
|---|---|---|
| 发布报"调用 X 不可用：工程里找不到" | 名字解析不到，或工程模块没登记对 | 工程页「接口」看探测结果；确认子模块名 |
| 发布报"没有参数 xxx" | 参数名和真实签名不一致 | 按属性面板提示的签名改 |
| 运行报"工程里找不到 plot_window" | 该库的解释器没装依赖 | 工程解释器填库自己的 venv |
| 图不显示 | 返回的是路径但文件不存在，或写的是 `show_plot` 弹窗 | 用 `save_plot` 这类返回文件路径的函数 |
| 待办里没有图 | 判定节点没写 `evidence` | 指向出图节点 |
| 报"输出 X 不能转成 JSON" | `out` 指向了对象 | 改指标量字段，或先落文件再传路径 |
