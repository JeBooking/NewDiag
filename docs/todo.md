## 失败原因区分（待拍板）

**诉求**：把「程序执行错误」和「诊断没找到原因」分开。

**现状**：状态层已分开——没找到原因走 escalation，落到 `escalated`；只有业务接口抛异常才落到 `failed`。混在一起的是 `failed` 一个桶，里面装了四类原因：

| error 前缀 | 含义 |
|---|---|
| `execution/*` | 业务接口真的报错 |
| `route/*` | 流程走不下去（判定不了是/否、分支没有后继） |
| `plan/*` | 计划层问题 |
| `signature/*` | 接口签名变了 |

run 层用前缀区分得很清楚，实例层和 UI 没有暴露，界面统一显示「失败」。

**建议**：实例加可空字段 `failure_kind`（`execution` / `route` / `plan` / `signature` / `unknown`），从 run 的 error 前缀聚合，状态枚举不动。

- 影响面：`models.py` 加列、`schemas.py` Detail 加 `failureKind`、实例列表与详情补标签、spec 加一句
- 迁移：老数据可从 `runs.error` 前缀反向回填；不回填只显示「原因未知」
- 已否掉：新增 `error` / `executionError` 状态——与 `failed` 语义重叠，要动终态集与终止/回退白名单，历史 `failed` 无法区分

**关联问题（同源，需一并拍板）**：收敛优先级 `success > escalated > failed`。一条路径报错、另一条 success 时，实例最终算 `success`，报错被静默吞掉。建议不动收敛规则，只在 payload 带 `hasExecutionError`，详情页提示「某路径执行出错但整体已上升」。

**状态**：未开工。

## 工程登记只记路径、业务代码不在平台（待拍板）

**诉求**：登记的工程应该能被「上传」，否则每个用户的机器上都得有这份代码，路径还必须一模一样。

**现状**：`projects` 表只有 `id / name / path / module / python / factory`，`path` 是**服务器本机的绝对路径**；`POST /projects` 只做重名检查加一行 INSERT，不探测、不复制、不校验目录内容。启动时 `codegen.prepare` 按这个路径复制源码到实例目录，所以登记本质上仍是一个指针，工程本体从未进入平台；换机器部署或两个人各用各的目录都会失效。

**候选方向**（代价从低到高）：

- **保持现状（单机单用户自用）**：把「工程目录必须在服务器上且路径固定」写进部署文档。零成本零风险，多人、换机不可用
- **相对路径 + 约定根目录**：登记只存相对路径，部署时把根目录整体挂载或同步；影响面小，存量登记要归一化
- **上传工程包（zip）**：上传 → 内容寻址存储 → 登记存摘要 → 运行时解包到实例级目录；新增上传接口与目录生命周期管理
- **外部制品库（git / 制品库）**：登记存坐标，运行时拉取到本地缓存；需凭证管理与缓存失效

**共同前提**：第三方依赖跟着代码走，还是留在宿主机。这决定「上传 zip」是「传源码」还是「传环境镜像」，工程量差一个量级。

**状态**：未开工。这是产品决策（单机自用 vs 多人协作），不是纯技术选型。

## 对象快照的恢复边界（暂缓）

**当前决定**：业务对象按普通 Python 成员整体快照，恢复不重跑构造器和业务方法。

**后续再讨论**：哪些成员是真正的业务状态，哪些是应排除或重建的连接、客户端、文件句柄、锁、窗口等运行资源；自定义对象、序列化钩子和代码升级的兼容规则；大对象快照与已取数据重复保存的体积及耗时。

当前序列化失败明确报错，不静默丢弃成员，也不以重新采集代替恢复。

## 待复核（本轮改动后的静态观察，未逐条复验）

- 流程启动表单的请求失败时，页面仍可能显示「没有声明启动参数」并允许提交；从版本 A 快速切到 B 时，迟到的 A 响应可能替换 B 的表单
- 实例详情初次加载遇到网络或服务器错误时也显示「实例不存在」，建议只对 404 显示不存在，暂时性故障提供原地重试
- 保存请求发出后仍可编辑，响应回来会清掉 dirty 并回填服务端文档，可能覆盖请求发出之后的输入
- 键盘移动节点后直接保存，位置可能没有写回 doc
- 重启后未完成实例一直停在 running/waiting，缺少启动时批量标记中断的清理逻辑

## 接入工程的版本绑定（待研究）

现状：发布**不固定模块代码实现**，只冻结接口指纹（`releases.signature_json`，实例还没有 run 记录时比对）。执行时按发布版本复制一份源码到 `data/modules/<releaseId>`，同版本实例共用；此前是每个实例整份复制（`6e9aef3`），磁盘随执行次数增长。

需要再研究：

- 是否提供「不复制、直接引用原工程路径 + 指纹校验」模式：省空间，代价是两次执行之间工程代码可能被改
- 快照粒度：按发布 id 还是按工程内容哈希（同一份代码多次发布可复用同一目录）
- 清理策略：发布版本没有删除入口，`data/modules` 会随发布数只增不减
- 指纹校验目前只在实例首次执行前比对，跑过节点后不再拦；是否每次子进程启动都校验
- 与「发布即冻结」的语义对齐：如果把代码快照也算进发布产物，发布体积和回滚行为都要重新定义
