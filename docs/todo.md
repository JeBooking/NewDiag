## 工程登记只记路径、业务代码不在平台（2026-11-05 提出，待拍板）

**诉求**：登记的工程应该能被「上传」，否则每个用户的机器上都得有这份代码，而且路径必须一模一样才能用。

**核实结论**：`projects` 表只有 `id / name / path / module / python / factory / created_at`（`models.py:181-189`），其中 `path` 是**服务器本机的绝对路径**；`POST /projects`（`api/projects.py:48-70`）只做重名检查加一行 INSERT，既不探测、也不复制、也不校验目录内容。运行期 `scheduler._project()` 按工程标识查当前登记行（`scheduler.py:1078-1084`），`sessions._spawn` 直接把这个 `path` 当 `cwd` 起子进程（`sessions.py:60`、`:193`）。所以「登记」本质上只是一个指针，工程本体从未进入平台；换一台机器部署、或两个人各用各的目录，都会失效。

**候选方向**（代价从低到高）：

- **保持现状（单机单用户自用）。** 不改代码，把「工程目录必须在服务器上且路径固定」写进部署文档。零成本零风险，但多人、换机都不可用；日后要改仍需一次性迁移（把本地路径换成引用）。切换成本最低、天花板也最低。
- **相对路径 + 约定根目录。** 登记只存相对路径，部署时把根目录整体挂载或同步。影响面：`path` 语义变更、`sessions._spawn` 的 `cwd` 拼接、启动前校验根目录存在；模型字段不用改。包内相对 import 不受影响（目录结构不变），**第三方依赖仍由部署方预装在该目录的 venv 里**，平台不碰。切换成本：存量登记要归一化（绝对值 → 相对值），漏改的工程会直接起不来。
- **上传工程包（zip）。** 上传 → 复用现有内容寻址存储或新建表 → 登记存摘要 → 运行时解包到实例级目录再起子进程。影响面最大：新增上传接口、`projects` 加摘要列或新表、调度器要管解包目录的生命周期（回退、重跑、多实例并发都要复用同一份包），探针也得指向解包目录。包内相对 import 只要结构完整就不会坏；**依赖不会跟着走**——要么要求包内带 `requirements.txt` 由平台安装（等于让平台执行用户代码里的安装脚本，安全和耗时都成问题），要么继续依赖宿主预装。切换成本最高，但这是唯一能真正做到「别人也能用」的方向。
- **外部制品库（git / 制品库）。** 登记存坐标（仓库 + ref + 子目录），运行时拉取到本地缓存再起进程。影响面居中：新增拉取层、凭证管理、缓存失效；内网离线环境还要自建镜像。相对 import 不坏；**依赖问题与上一条相同**，除非制品本身就是完整环境镜像（那时工程量再上一个台阶）。切换成本落在运维侧。

**共同前提**：四个方向都要先回答同一个问题——**第三方依赖跟着代码走，还是留在宿主机**。这决定「上传 zip」到底是「传源码」还是「传环境镜像」，两者工程量差一个量级；不先定这一条，选方向会反复改。

**影响面**：涉及 `models.py`（加列或新表）、`api/projects.py`（登记/上传接口）、`services/sessions.py` 与 `scheduler.py`（`cwd` 与目录生命周期）、`services/signatures.py` 与 `worker/probe.py`（探针指向哪里），以及部署文档与存量数据迁移。[登记](../backend/app/api/projects.py#L48) · [运行时取工程](../backend/app/services/scheduler.py#L1078) · [起子进程](../backend/app/services/sessions.py#L193)

**与既有条目的关系**：与「删除业务工程前列清引用范围」同源，都指向「登记只是一行指针」这个前提；方向一旦改成引用摘要或坐标，那条的删除语义也要跟着重写，不要分开做。

**状态**：未开工。这是产品决策（单机自用 vs 多人协作），不是纯技术选型；建议先落方向一（把限制写进部署文档），把方向二作为下一步最小改动。

## 全项目审视

审视基线为 `71f6608`，并在 `23bb0bc` 上复核（2026-11-04）。本文记录候选工作和验收方法，已确定的产品契约以 [设计说明](spec.md) 为准。P1 指可能造成工作丢失、错误结果或阻塞诊断的问题，P2 指可恢复的误操作、信息缺口或需先验证的成本。下列“验收”是未来验证步骤；本轮为代码和文档静态核查，未运行浏览器、故障注入或负载实验。

### API、文件与交付

- **P1 · 大流程包应在读入时限流（实现缺口）。** 导入接口先无上限 `await file.read()`，再把整个字节串交给有 200 MiB 上限的解析器。超限文件会在拒绝前占用应用内存。建议按块计数，超过上限立即返回 413，保留已有的解压大小限制。验收：在请求不声明长度时上传超限文件，仍提前拒绝且不创建流程；限内合法包正常导入。[导入入口](../backend/app/api/flows.py#L451) · [解析器限额](../backend/app/services/packages.py#L39)
- **P2 · 导入结果列出缺失附件（体验建议）。** 包内找不到引用的文件时服务端只记警告并保留哈希；若目标库也无此文件，接手者可能到执行时才发现资料打不开。建议区分“目标库已有”和“两边都缺”，在导入结果中列出需补齐的节点和文件。验收：同一份缺附件的包分别导入已有、没有对应文件的库，只有后者显示缺件清单。[缺件处理](../backend/app/api/flows.py#L489)
- **P2 · 删除业务工程前列清引用范围（需产品决策）。** 删除接口直接移除登记行，而运行时按工程标识查询当前登记。新启动的诊断可能因此失去已发布步骤使用的工程。建议先展示受影响的流程版本，再决定禁止删除被引用工程，还是改用停用和迁移。验收：同一工程分别被草稿、发布版本引用以及无引用时，操作者能在最终确认前区分影响并按选定策略处理。[删除](../backend/app/api/projects.py#L94) · [运行时查询](../backend/app/services/scheduler.py#L1078)
- **P2 · 「排查方法」下拉每次打开都要等 1~5 秒（性能）。** 根因是 `probe()`（`backend/app/services/projects.py:99`）每次都 `subprocess.run([python, probe.py])`，重新启动解释器并 import 业务模块，模块里带 pandas／matplotlib 时更慢；全链路没有任何缓存。前端 `DiagnosisMethodEditor.vue:18-24` 还先 `listProjects()` 再 `fetchProjectFunctions()` 串行两个请求，节点面板由 `v-if` 控制（`src/views/FlowDesigner.vue:506`），取消选中再点会重建组件、重新请求。建议前端按工程 id 缓存请求，`DiagnosisMethodEditor`／`BindingEditor`／`FlowDesigner` 三处共用一份，另给显式「刷新接口」按钮做失效；后端 `probe()` 加 30~60 秒 TTL。不拆接口——瓶颈在解释器启动和 import，不在传输。验收：同一工程第二次打开下拉 ≤200ms；改完业务代码点「刷新接口」能看到新增方法；三个入口命中同一份缓存。[探针](../backend/app/services/projects.py#L99) · [方法编辑器](../src/components/panels/DiagnosisMethodEditor.vue#L18)

### 调度、业务调用与恢复

- **P1 · 文件字段默认值应走同一条存储校验路径（实现缺口）。** 当人工采集字段有包含 `hash/path` 的默认值、请求又省略该字段时，调度器不会解析该引用。worker 随后填入默认值，只检查哈希类型。若业务函数按其中的路径读文件，可能访问服务账号可读的上传目录外文件。建议在统一补齐默认值后用平台存储解析路径。验收：哈希有效但路径伪造时只允许平台解析出的路径；哈希失效时在业务函数调用前拒绝，合法已上传文件仍可用。[调度器](../backend/app/services/scheduler.py#L656) · [worker 校验](../backend/app/worker/node_sdk.py#L69)
- **P1 · 超时应覆盖向业务进程发送请求（实现缺口）。** worker 在读请求前加载业务模块。若初始化卡住、大请求填满管道，调度器可阻塞在 write/flush，响应超时计时尚未开始。建议为发送和接收共用截止时间。验收：用阻塞初始化与超管道容量的负载触发，确认限定时间内结束或重试，进程回收、实例留下明确失败原因。[发送与计时](../backend/app/services/sessions.py#L95) · [业务模块启动](../backend/app/worker/session.py#L45)
- **P1 · 调度器不可用时别让诊断显示“运行中”（实现缺口）。** 调度模块导入失败会切换到空实现，启动方法直接返回，而启动接口已写入实例。建议拒绝启动或将本次实例明确置为失败。验收：模拟依赖导入失败，用户收到可操作的错误，不产生无人推进的 running 记录。[降级实现](../backend/app/api/instances.py#L32) · [启动调用](../backend/app/api/instances.py#L250)
- **P1 · 重启后区分中断与人工等待（需产品决策）。** 启动时初始化数据库，正在执行的调度线程却随旧进程消失。建议先识别中断并解释，再决定哪些动作允许人工重试；不要默认重新调用可能有外部副作用的业务代码。验收：分别在调用中、等待人工时重启，核对状态、历史、可用操作与执行次数。[应用启动](../backend/app/main.py#L36) · [既有待决事项](spec.md#11-尚未决定)

### 从发布版本到执行记录

- **P1 · 启动按钮应与已加载的发布版本表单绑定（实现缺口）。** 表单请求失败时页面仍展示“没有声明启动参数”和 JSON 输入，并允许提交；从版本 A 快速切到 B 时，迟到的 A 响应也可能替换 B 的表单。建议按发布 ID 接收响应，加载失败提供重试，只有成功确认无参数才显示自由输入。验收：延迟 A 或令 B 返回 500，不能对 B 提交 A 的参数，B 加载成功后可启动。[版本切换](../src/views/FlowReleases.vue#L88) · [启动按钮](../src/views/FlowReleases.vue#L286)
