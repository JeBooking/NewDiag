# 既有工程的可视化组合接入方案（提案）

状态：旧提案。架构建议已由 [基于当前实现的重新分析](integration-architecture-analysis.md) 替代；本文保留早期讨论记录，不作为实施依据。现行契约仍以 `spec.md` 为准。

目标：用户可以登记工程、选择接口、配置对象和绑定参数；由平台承担调用、数据传递、展示和结果适配，不要求用户新建集成项目、继承 SDK 或手写胶水代码。

## 1. 基于三个工程的判断

本次仅静态阅读源码，未运行外部工程。

| 工程 | 已有可复用接口 | 接入所需的适配 |
|---|---|---|
| MockDataService | `dataclient.DataClient(root, interval)`；`fetch(...)` 返回 `pathlib.Path` | 构造普通类、把返回路径登记为数据文件 |
| PlotEngine | `dataset.Dataset.load(path)` 返回 Dataset；`Dataset.plot_series(...)` 返回曲线字典；`plot_window.save_plot(data, path, ...)` 导出图片 | 接收对象返回值、调用对象方法、收集图片 |
| JudgeEngine | `judgekit.JudgeEngine(thresholds=...)`；`judge_series(item)` 返回 Verdict 列表；`summary(verdicts)` 返回字典 | 构造参数、在同工程内传递对象列表、将 `overall/reasons` 映射为判断与依据 |

`PlotEngine/Flow.py` 已包含一部分整合逻辑，但方案直接复用上述基础接口，不要求继续在 FlowClass 中增加业务串联代码。

源码接口层面，这三个工程具备不改业务代码的组合条件；解释器依赖及运行环境仍需接入时检查。

## 2. 核心设计：工程能力、调用步骤、诊断节点分开

### 工程能力

工程管理继续登记路径和解释器，新增模块、普通类、构造方法、类方法和实例方法的选择能力。一个工程可选择多个模块，例如 PlotEngine 中的 `dataset` 和 `plot_window`，无需复制登记同一个工程。

扫描提供接口候选和参数签名，不擅自推断哪个方法负责取数、哪个字段代表异常。无类型注解的参数，由用户选择类型；返回结构可通过用户主动发起的试调用获得样例。

扫描尽量先读取源码；需要导入确认的接口放在隔离进程中处理。不能为扫描自动调用业务方法或实例化所有类。

### 调用步骤

每个自动节点内部提供有顺序的步骤列表，支持：

- 创建对象，例如 `DataClient(...)`、`JudgeEngine(...)`。
- 调用模块函数、类方法，例如 `Dataset.load(...)`。
- 调用已有对象的方法，例如 `dataset.plot_series(...)`。
- 选择返回字段、收集文件、配置页面展示、映射判断结果。

参数来源通过控件选择：启动表单、常量、前一步结果、上游节点产物、当前工程对象、平台分配的输出路径。支持字典和列表常量以及字段路径，不要求用户填写 Python 表达式。

对象创建可设为本次诊断首次使用时执行；业务调用默认按节点实际到访执行。取数是否复用必须明确配置，不能因为参数相同就永久复用旧数据。

### 诊断节点

主画布保留开始、数据准备、排查、处置、结论、终止等业务语义。内部步骤不全部暴露为主图节点。

数据准备节点配置取数与加载；排查节点配置选曲线、绘图、判断和结果展示。同一组合保存为可复用模板，后续只替换指标、阈值或数据源。

四阶段可作为快捷模板，内部允许多次调用，不再要求每阶段只能对应一个符合固定返回协议的函数。

## 3. 三工程的具体配置

在页面登记三个工程及各自 Python 解释器，选择以下模块：

| 工程路径 | 模块 |
|---|---|
| `D:\FILE\Projects\MockDataService` | `dataclient` |
| `D:\FILE\Projects\PlotEngine` | `dataset`、`plot_window` |
| `D:\FILE\Projects\JudgeEngine` | `judgekit` |

创建“数据准备”节点，在步骤编辑器中配置：

| 步骤 | 选择的接口 | 页面绑定 | 命名结果 |
|---|---|---|---|
| 1 | `DataClient(...)` | root：平台分配的本次调用输出目录；interval：保留默认值 | client 对象 |
| 2 | `client.fetch(...)` | device_id、activity、start_time、end_time：启动表单；metrics：可选列表 | 数据文件 |
| 3 | `Dataset.load(path)` | path：步骤 2 的数据文件，在 PlotEngine 进程中的本地路径 | dataset 对象 |

创建“振动是否异常”排查节点，配置：

| 步骤 | 选择的接口 | 页面绑定 | 命名结果 |
|---|---|---|---|
| 1 | `dataset.plot_series(...)` | device、activity：启动表单；metric：vibration | series |
| 2 | `save_plot(data, path, ...)` | data：series；path：平台生成的 PNG 输出路径；title：节点标题 | 图片文件 |
| 3 | `JudgeEngine(...)` | thresholds：在字典表单中填 peak、mean、trend 阈值 | judge 对象 |
| 4 | `judge.judge_series(item)` | item：series | verdicts |
| 5 | `judge.summary(verdicts)` | verdicts：步骤 4 的原始返回值 | summary |

节点结果配置：

- 判断字段：`summary.overall`，yes → 是分支，no → 否分支；缺字段或其他值报执行错误。
- 判断依据：`summary.reasons`，按列表展示；为空时使用平台模板“配置的规则均未触发”。
- 页面展示：步骤 2 的图片、`summary.verdicts` 规则明细表、判断依据。
- 自动或人工：选择自动则调用判断步骤；选择人工则展示曲线并等待人选是/否及填写依据。

本例的 `JudgeEngine` 默认执行 peak、mean、trend 三条规则，overall 表示任一规则触发。只检查峰值时，应改选已有 `PeakThresholdRule(threshold).evaluate(y)`，并映射返回对象的 result/reason；仅配置 peak 阈值不会关闭另外两条规则。

主流程可以连接为：开始 → 数据准备 → 振动排查 → 是：异常结论／人工处置；否：下一项排查。各路径继续按现有规则连接问题解决或上升。

增加温度排查时复用 dataset，将 metric 改为 temperature，并按业务要求选择规则；无需复制取数、读文件和组装展示的代码。

## 4. 平台需要承担的运行语义

### 对象和跨工程数据

每个诊断实例按需启动各工程 worker，使用各自解释器和工作目录。同工程内对象通过句柄传递，Dataset 和 Verdict 列表保持真实 Python 对象，不能先转成 repr 再调用下游。

跨工程默认传递 JSON 值和平台管理的文件引用。本例中 Dataset 留在 PlotEngine，series 作为 JSON 交给 JudgeEngine，Verdict 列表留在 JudgeEngine 中交给 summary。不要求不同解释器共享业务对象或安装对方工程。

文件传递先归档不可变内容，再为目标 worker 提供本地读取路径；服务在不同机器时需要传输内容，不能直接透传源机器绝对路径。初期范围可限定为同一后端机器的多工程、多解释器。

### 人工等待、回退和复用

沿用按具体到访与 generation 定位数据版本的原则。文件内容、曲线数据和可保存对象组成检查点；人工等待之后从该检查点恢复，不默认重新调用取数接口。

Dataset 等可序列化对象可在本工程解释器中保存恢复；不可序列化对象必须明确采用“仅驻留内存”或受限的重建策略。重建只能使用已固定的输入和产物，以及明确允许重放的操作；不能静默重新取数或执行有副作用的方法。平台重启自动续跑不包含在本提案首期范围内。

分支只读取当前父链的有效产物。并行使用共享可变对象时必须串行化访问或采用分支副本；不让两个分支竞争修改同一个 dataset 选择状态。本例直接给 plot_series 传 device/activity，避免依赖 `FlowClass.prepare()` 的可变选择状态。

重新采集产生新文件版本；重新绘图／判断默认复用所选到访的数据版本。缓存和对象恢复都不能越过回退边界串用较新的结果。

### 文件与图表

调用前分配独立输出目录和文件名，避免 DataClient 同参数取数时覆盖历史文件。调用成功后由平台收集指定返回路径，不把任意返回字符串自动当成文件。

图片直接复用 `save_plot`，归档后在浏览器展示。首期提供静态图；桌面窗口及其工具栏不会自动迁移成浏览器交互。

虽然 save_plot 本身不创建窗口，当前 plot_window 模块仍在导入时依赖 tkinter/TkAgg。接入检查应区分“可以导出图片”与“模块能在所选环境导入”；缺 Tk 时需要安装现有运行依赖，或最小改动地分离桌面导入。单纯设置 Agg 不足以消除顶层 Tk 导入依赖。

### 发布和记录

发布冻结调用顺序、对象配置、参数绑定、字段映射、展示配置及接口指纹。继续沿用现有发布版本、人工待办、回退和终止机制，不以业务脚本的执行循环替代调度器。

每步记录工程、目标接口、有效输入或产物引用、输出摘要、耗时和错误；失败时指出具体步骤及参数来源。业务异常不能自动映射成“否”。有副作用或结果不确定的调用不自动重试。

## 5. 与现有实现的差距和首期范围

现有四阶段已经解决部分跨工程函数调用和参数选择，但还缺少：

1. 普通对象的可视化构造、对象返回值和实例方法调用链。
2. 每个阶段可组合多次调用，而非单个函数。
3. 文件路径与文件产物的显式映射、输出路径注入和跨 worker 读取。
4. 任意业务结果到 result/reason/presentation 的可视化映射。
5. 一个工程多个模块的能力目录，以及对象检查点的版本化管理。

当前诊断类模式要求整图绑定一个 SDK 业务类，并禁止与四阶段／准备节点混用；新方案不能只补几个前端选择器，必须扩展 doc、plan、探测及 worker 协议。

现有四阶段也会拒绝带 `**kwargs` 的函数，而 save_plot 包含 `**savefig_kwargs`。新调用器应允许只绑定明确列出的参数，并单独限制或配置扩展参数；无需用户为此手写一层无可变参数的包装函数。

首期只覆盖本例需要的同步 Python 调用、显式参数、对象方法、JSON／文件传递、静态图片、规则结果映射与人工判断；不做任意代码表达式、跨工程 Python 对象传递或桌面交互自动迁移。

建议实现顺序：普通对象调用与文件产物 → 调用步骤编辑及字段选择 → 展示与判断映射 → 检查点／回退集成 → 将本例保存为可复用模板。正式开发前，先把确认后的语义同步到唯一设计依据 spec.md，再同步契约与实现。
