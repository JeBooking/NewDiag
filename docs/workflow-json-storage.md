# Workflow JSON 存储格式：为什么 nodes 与 edges 分开存

> 对应 `src/domain/types.ts` 的 `FlowDoc`：`nodes: DocNode[]` + `edges: DocEdge[]` 两个数组分开存。
> 本文只回答一个设计问题：为什么不把「下一个节点」嵌进节点里（链表式），而要拆成两条边表。

## 结论（一句话）

诊断流程是 **DAG（有向无环图）**，不是线性链表。边表（edge list）是图的自然存储；链表只能表达严格串行，表达不了分支、汇聚与并发。

## 一、为什么这里根本不是链表场景

链表的约束是「每个节点只有一个后继」，只能表达一条线。而诊断流程是图：

| 结构 | 项目里的实例 |
|---|---|
| 分支 | `investigation` 节点 `yes` / `no` 双出边（`DocEdge.branch`） |
| 汇聚 | 多个节点指向同一个 `conclusion` / `problemSolved` |
| 并发 | `mode: "parallel"`，多 token 同时推进，无固定先后 |

这三种结构一旦出现，链表模型直接失效——「下一个」不再唯一，甚至不存在。

## 二、分开存的六个理由

1. **与渲染层模型对齐**：前端用 `@vue-flow/core`，其数据模型本身就是 `nodes[] + edges[]` 两个数组。存储格式与画布模型同构，加载即用，省一层转换。

2. **边自身有语义**：`branch`（yes/no）、`order`（多出边排序）是**边的属性**，不是节点的。链表只能把「后继」挂在节点上，但「这条边是 yes 还是 no、排第几」属于分叉本身，无从挂靠。

3. **独立编辑与校验**：边用显式 id 引用 `from`/`to`，指向不存在的节点就是「悬空边」，可单独 lint；删一个节点不用改前驱的 next 指针（链表式删节点必须回头改前驱，否则悬挂）。

4. **JSON 天然友好**：边表是「关系平铺」，一行一条边，无环、无重复。链表式要么嵌套（下游节点被重复内联），要么指针引用（形成环，序列化困难）。

5. **编译要随机访问**：`compiler.py` 要按 `from`/`to` 建邻接表、做拓扑排序、查「谁指向我」。边表就是邻接表，随手可得；链表的反向查找（找所有前驱）代价高。

6. **与执行模型同构**：编译产物 `Plan` 里的 `next: Record<id, string[]>` 本身就是「节点 → 后继列表」的邻接表。doc 的边表编译后**直接映射**成 `next`，链表反而要再多一步折成数组。

## 三、链表什么时候才合理

仅当流程**严格线性**：无分支、无汇聚、单 token 串行。本项目的 `mode` 已允许 `parallel`，且分支/汇聚是常态，前提不成立。

## 四、一句话定性

nodes + edges 分开存 = **邻接表的 JSON 形态**，不是实现偷懒，而是图结构、渲染层模型、编译器三者的共同约束逼出来的选择。
