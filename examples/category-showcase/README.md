# 分类节点与手动模式示例

一条诊断流程同时演示 v1.19 的两种模式：**手动模式**下分类节点把人选的一条思路交给人工逐节点点完，**自动模式**下分类节点被穿透、三条思路全部自动执行；停在半路还能「转自动」，平台补跑开始节点后接着走。

三个外接工程直接复用 [`../slot-showcase/`](../slot-showcase/)，本目录只有 `workflow.json` 和这份说明，没有复制任何代码。

## 登记与运行

| 名称 | 目录 | 模块 |
|---|---|---|
| `示例数据源` | `examples/slot-showcase/data_source` 的绝对路径 | `feeder` |
| `示例处理展示` | `examples/slot-showcase/analytics` 的绝对路径 | `render` |
| `示例判断` | `examples/slot-showcase/judge` 的绝对路径 | `rules` |

导入 `workflow.json` → 保存 → 发布 → 启动，启动参数全部用默认值即可：

| 参数 | 默认 | 作用 |
|---|---|---|
| `dataset` / `device` | `cat-2026-11` / `M-1` | 构造 `DataCenter` |
| `points` | `24` | 振动、温度两条排查的取数点数 |
| `threshold` | `5` | 振动判定阈值，改大就能让振动判「否」 |
| `tempLimit` | `80` | 温度判定阈值，改到 `90` 以上就能让温度判「否」 |

> 通道说明：`feeder.catalog()` 里只有 `vibration` 与 `temperature` 两个真实通道，没有 `voltage`。所以第三条出线没有硬造电压通道，而是改成**同通道的长样本复核**（`temperature` + `points=48`），用更宽的裕度阈值 `92` 判定，正好在默认参数下走出「否」这一条路。

## 流程

13 个节点，一条分类、三条排查、三条结论、三条处置、一个共用的问题解决和一个上升：

```
开始（构造 6 个对象，预热一段振动数据）
  → 分类「按现象缩小范围」
      ├─ 振动排查   ──是→ 振动超限   → 更换轴承并复测 ┐
      │              └─否→ 上升                      │
      ├─ 温度排查   ──是→ 温度偏高   → 清理散热并复测 ├→ 问题解决
      │              └─否→ 上升                      │
      └─ 温升趋势排查 ─是→ 温升裕度不足 → 加装散热并复测┘
                     └─否→ 上升
```

三条排查节点用的是同一条工程链，只有 `channel` 和判定对象不同：

```
feeder.DataCenter.fetch(channel=...) → render.Processor.smooth → render.Renderer.metrics（指标卡）→ rules.Judge.check
```

默认参数下的自动结果是：振动判「是」、温度判「是」、温升趋势判「否」（峰值 83.7 < 92），所以一次启动就能同时看到「结论→处置→问题解决」和「上升」两条路。

## 手动模式

启动时模式选「手动」（`runtime.mode="manual"`）：

1. 平台**一个槽位都不跑**——不复制源码、不生成 `flow.py`、不起子进程，创建实例后不会出现 `executions/` 目录。
2. 第一个待办就是分类节点，面板列出三个后继排查的标题（`振动排查` / `温度排查` / `温升趋势排查`），选一条提交。
3. 只有选中的那条排查会出待办；另外两条不产生 token，也不会有任何提示。
4. 排查待办展示 `observation` / `acquisition` / `assessment`，人填判断依据后选「是」或「否」。
5. 结论、处置都只是「继续」按钮；到达问题解决或上升后实例收敛，不生成待办。

手动模式下每次推进都写一条 `runs.source="manual"` 的记录，`output_json` 记着这次的选择（`{"choice":"vibration"}` 或 `{"result":"yes","reason":"..."}`）。

### 手动模式看什么日志

| 现象 | 日志 |
|---|---|
| 分类节点在等人选 | `手动等待节点 route（category）` |
| 排查在等人判断 | `手动等待节点 vibration（investigation）` |
| 结论 / 处置在等人点继续 | `手动等待节点 c_vibration（conclusion）`、`... r_vibration（remediation）` |
| 走完收敛 | `手动模式收敛：success` |
| 没跑过任何脚本 | 整个过程没有 `分支启动 ... pid=`、没有 `构造槽`、`data/executions` 为空 |

## 自动模式

同样一份流程，启动时选「串行」或「并行」（默认串行、上限 4）：

- 分类节点**被穿透**：它的三个后继顶上来成为开始节点的后继，分类本身不进 `NODES`、不产生 token、不产生 run。
- 并行且 `maxParallel ≥ 4` 时三条思路同时跑，各自的子进程、对象与缓存独立；串行时按深度优先一条条走。
- 自动判定走 `rules.Judge.check` 的返回值，结论与处置仍要人点「继续」。

### 自动模式看什么日志

| 现象 | 日志 |
|---|---|
| 三条思路分别起进程 | `分支启动 token=... node=temperature ... 模式=parallel 活跃=2 上限=4` |
| 每条排查跑完 | `节点 vibration 完成 branch=yes`、`节点 margin 完成 branch=no` |
| 同一参数命中缓存 | `拉取缓存命中 DataCenter.fetch` |
| 开始节点跑完构造与拉取 | `节点 start 完成 branch=default` |
| 分类没有执行 | 日志里**找不到** `node=route` 的 `分支启动` 或 `节点 route 完成` |

## 转自动

手动停在任意一个人的待办（分类、排查、结论、处置都行）时，实例详情里点「转为自动」（`POST /api/instances/{id}/switch-to-auto`，可带 `mode` / `maxParallel`）：

1. 平台先补跑开始节点的构造槽与拉取槽——这时才复制源码、生成代码、起子进程，`data/executions/` 下才出现目录。
2. 拿到带数据的对象后跳回刚才停住的那个节点，按开始节点补跑出的对象继续。
3. 人工已经走过的节点保留原选择，不重跑、不重复提问。
4. `runtime` 从 `{"engine":"manual/v1","mode":"manual"}` 变成 `{"engine":"python/v1","mode":"serial"}`；反向（自动→手动）没有入口，接口返回 409。

| 现象 | 日志 |
|---|---|
| 请求被接受 | `实例 xxx 手动转自动：mode=serial maxParallel=4` |
| 引擎重编译并从停住处续跑 | `手动转自动：serial/4，从节点 temperature 续跑（新代 2）` |
| 开始节点补跑 | `分支启动 ... node=start ... 模式=serial`，随后 `构造槽 name=center`、`节点 start 完成` |
| 继续人工停住的那一步 | `节点 temperature 完成 branch=yes` |

默认参数下建议试这一条：分类选「温升趋势排查」→ 判「否」→ 落 `上升`；再开一个实例停在「温度排查」待办直接转自动，能看到开始节点补跑后温度判「是」，一路走到问题解决。

## 自己配流程时怎么照抄

- 分类节点只写 `title` / `detail` / `position`，出线 ≥2 条、分支键全 `default`、目标只能是排查节点；`order` 就是选项顺序。
- 选项文案直接取目标排查的 `title`，不要另起一个分类名——手动模式面板原样展示它。
- 每条排查都要把 `yes` / `no` 都接上，手动模式选「否」才不会无路可走。
- 想在手动模式下让人看懂排查依据，把 `fields` 三个键写全；这三个键就是待办里展示的文字。
